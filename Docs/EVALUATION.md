## 2. Selection rationale

Selected on **validation RMSE** (never test): 1d → xgboost, 3d → gru, 7d → gru.
On the held-out test set the selected family beats both baselines on every
horizon with a small val→test gap (no overfit; test MAE is slightly *lower*
than validation, consistent with a calmer winter test window).
Note: the "xgboost" slot is sklearn HistGradientBoostingRegressor — native
XGBoost could not load on the training host (missing libomp). The comparison
remains fair (same features/splits/seeds); a native-XGBoost rerun is optional.

## 3. Transformer finding (closes Architecture §7 open question)

The Transformer is the **worst** of the four learned families on 3d/7d
(val MAE 4.80/5.14 vs GRU 4.55/4.82) and never selected. At ~25k ward-days,
attention adds no value over recurrence for this task. Recommendation: keep
the Transformer in the comparison harness (one-line evidence per retrain) but
exclude it from production serving until data volume grows ~10×.

## 4. Objectives verdict (PRD §3/§7)

- Ward-level 1/3/7-day forecasts: YES — live `/api/forecast`, MAPE ~3.3%, R² ≥ 0.99.
- Reservoir-aware recommendations: YES — `/api/supply-plan` never over-allocates (conservation asserted in e2e).
- Early stress detection: YES as an engine (canonical 500/450 → WAR 0.90 Moderate reproduces); see §5 for data limits.
- Product journey (admin → citizen → complaint round-trip): YES — e2e 31/31 + pytest 11/11 on bmc-v1.
- Onboarding from docs: YES — `Docs/` + `Context.md` current.

## 5. WAR calibration (P0-2)

Method: `scripts/war_calibrate.py` on merged ward-daily data.
Findings: ward WAR (equal-split gross storage ÷ demand) ranges ≈ 2.9–4000,
median ≈ 184 — reservoir-gross scale, so absolute bands 1.0/0.85/0.70 leave
all BMC ward-days Safe. Daily-yield framing (Σ Yield_MLD = 4273 vs city
demand ≈ 3300 ML/day) confirms structural surplus: **no absolute scarcity
exists in the 2023–2025 window**. This is a dataset property, not an engine
failure — the engine is proven by the canonical example, boundary unit tests
(`test_stress.py`), and the synthetic scarcity planner test.
Decision: keep absolute bands (explicit in `.env` + compose, no longer
defaults-only); record municipal validation of absolute thresholds as required
before any production/regulatory use.

## 6. Supply-plan verification

Rule-based allocator (severity-weighted pro-rata, forecast caps, water-filling
redistribution, 5% reserve): e2e asserts pool conservation and high-stress
prioritization live. An LP-optimal engine (`backend/app/planner_lp.py`,
PuLP/CBC, same contract, 5 unit tests) ships beside it, selected via env
`SUPPLY_OPTIMIZER=rule|lp` (default `rule`). Dashboard exports the plan as CSV.

## 7. Retraining + registry policy (decision)

- Registry: `models/manifest.json` regenerated by `scripts/registry.py` after
  every retrain (active families, SHA-12 artifact hashes, metrics, splits).
- Policy: **monthly scheduled retrain** on new readings + **MAPE-guard trigger**
  (validation MAPE regresses >1pt vs manifest → retrain out of cycle).
  Cron/automation itself is deployment scope (Phase 15), not implemented here.

## 8. Known limitations

1. `level_m` is a placeholder (`storage_pct × 0.5`) — never use for engineering.
2. Reservoir→ward serving map is a synthetic modelling assignment, not BMC operations.
3. GIS polygons are centroid boxes, not authoritative boundaries.
4. D7 complaints/schedules not ingested (complaints API is manual CRUD).
5. Supervised leakage classification needs real labels (unsupervised only).
6. Absolute WAR bands need municipal validation (see §5).
